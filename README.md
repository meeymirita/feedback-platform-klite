# feedback-platform-klite

Мини-платформа для ежедневной и еженедельной отчётности сотрудников.

**Стек:** Vue 3 + TypeScript · NestJS + TypeScript · PostgreSQL · Docker

```
.
├── backend/                 — NestJS API (JWT, TypeORM/Prisma, ExcelJS)
│   ├── Dockerfile
│   └── .dockerignore
├── frontend/                — Vue 3 SPA (Vite, Pinia, Vue Router)
│   ├── Dockerfile
│   ├── Caddyfile            — Caddy: раздача SPA + прокси /api + авто-HTTPS
│   └── .dockerignore
├── docker-compose.yml       — прод-стек: postgres + backend + frontend (Caddy)
├── docker-compose.dev.yml   — overlay для разработки (watch/HMR, bind-mount)
├── .env.example             — образец переменных окружения
├── docs/
│   ├── DOCKER.md            — построчная документация по всем Docker-файлам
│   └── DEPENDENCIES.md      — все библиотеки проекта с версиями и назначением
└── README.md                — этот файл (ТЗ v1.0)
```

---

## Запуск в Docker

```bash
cp .env.example .env          # заполнить пароли и JWT-секреты

# Прод: postgres + backend (NestJS) + frontend (Caddy, HTTPS автоматически)
docker compose up --build -d
#   → https://localhost:8443   (HTTP :8080 редиректит на HTTPS)

# Разработка: авто-перезапуск backend, HMR фронта, исходники с хоста
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
#   → http://localhost:8080
```

Точка входа — контейнер **Caddy**: отдаёт собранный SPA, проксирует `/api/*` на
backend и сам поднимает HTTPS (внутренний CA для `localhost`, Let's Encrypt для
реального домена — задаётся через `SITE_ADDRESS` в `.env`).

Полное описание каждого файла (Dockerfile, Caddyfile, compose, .dockerignore,
.env) с построчными пояснениями — в **[`docs/DOCKER.md`](docs/DOCKER.md)**.
Список всех зависимостей с версиями и назначением — в
**[`docs/DEPENDENCIES.md`](docs/DEPENDENCIES.md)**.

# Техническое задание (TZ_reports_platform_1)

**Мини-платформа для ежедневной и еженедельной отчётности сотрудников**
Версия: 1.0
Стек: Vue 3 + TypeScript / NestJS + TypeScript / PostgreSQL / Docker

## 1. Цель проекта

Внутренний веб-сервис, в котором каждый сотрудник ежедневно фиксирует, над какими
задачами он работал (проект, ссылка на задачу в Bitrix24, что сделал, сколько
времени потратил). В конце недели система автоматически собирает эти записи в
единую таблицу-отчёт по каждому сотруднику, которую можно выгрузить в Excel.

**Ключевая идея:** заменить ручной сбор отчётов в мессенджере/документах на
структурированную форму + автоматическую агрегацию.

## 2. Роли и права доступа

| Действие | Сотрудник | Админ |
| --- | :---: | :---: |
| Вход по email/паролю | ✅ | ✅ |
| Добавление/редактирование своих записей отчёта | ✅ | ✅ (если админ тоже ведёт отчёт) |
| Просмотр своих ежедневных записей | ✅ | ✅ |
| Просмотр своего еженедельного отчёта | ✅ | ✅ |
| Просмотр отчётов любого сотрудника | ❌ | ✅ |
| Список сотрудников, создание/блокировка аккаунта | ❌ | ✅ |
| Назначение роли (сотрудник/админ) | ❌ | ✅ |
| Экспорт своего отчёта в Excel | ✅ | ✅ |
| Экспорт отчёта любого сотрудника / сводного по всем | ❌ | ✅ |

**Регистрация — закрытая:** аккаунты создаёт админ вручную (имя, email, временный
пароль, роль). Самостоятельной регистрации нет.

## 3. Функциональные требования

### 3.1 Аутентификация

- Вход по email + пароль.
- JWT (access token в памяти/на клиенте + refresh token в httpOnly cookie).
- Смена пароля из личного кабинета.
- Сброс пароля админом (генерация нового временного пароля) — без email-рассылки
  на первом этапе, если своей почтовой инфраструктуры нет.

### 3.2 Личный кабинет сотрудника

**Добавление записи отчёта** (в любой день, включая прошедшие в пределах недели):

- Дата (по умолчанию — сегодня)
- Домен проекта (текст, например `biomaster.pro`)
- Ссылка на задачу (URL, например ссылка на Bitrix24)
- Что сделал (многострочный текст)
- Время, затраченное на задачу (ввод в формате `чч:мм` или минутами через степпер)

За один день можно добавить сколько угодно записей (одна задача = одна запись).

**Список своих записей:**

- Отображение по дням, с возможностью редактировать/удалять запись только пока
  текущая неделя не закрыта (см. 3.4) или без ограничения — уточняется отдельно
  (см. раздел 8, открытые вопросы).

**Еженедельный отчёт** (только просмотр + экспорт):

- Автоматически формируется из всех записей сотрудника за выбранную рабочую
  неделю (понедельник–пятница).
- Таблица со структурой как в образце:

| Дни недели | Задачи (домен) | Ссылка | Время |
| --- | --- | --- | --- |
| Понедельник | stena-nso.ru | https://... | 3:30 |
| | dkedra.ru | https://... | 1:30 |
| Вторник | condor-nsk.ru | https://... | 3:50 |
| ... | ... | ... | ... |

- Внутри дня — построчно все записи, без суммирования одинаковых доменов (как в образце).
- Итоговая сумма времени за день и за неделю — строкой снизу/сбоку (полезное
  дополнение к образцу).
- Переключение недель (стрелки «предыдущая/следующая неделя» или выбор диапазона датой).
- Кнопка «Скачать в Excel» — генерирует `.xlsx` в формате образца.

### 3.3 Панель администратора

- **Список сотрудников:** имя, email, роль, дата последней записи, статус
  (активен/заблокирован). Создание, редактирование, блокировка сотрудника.
- **Просмотр отчётов:** выбор сотрудника + недели → та же таблица еженедельного
  отчёта, что видит сам сотрудник.
- **Сводный отчёт по всем сотрудникам за неделю** (доп. функция): список
  сотрудников с суммарным временем за неделю, drill-down в отчёт конкретного
  сотрудника.
- **Экспорт:**
  - по одному сотруднику — отдельный `.xlsx` файл (та же форма, что видит сам сотрудник);
  - по всем сотрудникам — отдельный экспорт, где каждому сотруднику соответствует
    свой лист (sheet) в одном `.xlsx` файле, либо архив из отдельных файлов — на
    выбор реализации; логически это «пакет отдельных отчётов», а не один сводный
    лист с перемешанными данными.

### 3.4 Правила по времени/датам

- Редактирование и удаление записи доступно за любой прошедший день, без
  ограничения по сроку давности.
- Дедлайна на подачу отчёта и напоминаний нет.
- Жёстких ограничений/блокировок по сумме часов в день нет. Мягкая подсказка в
  форме: одна задача обычно не превышает 8 часов (не блокирует сохранение, просто
  предупреждение в UI).
- Рабочая неделя: понедельник–пятница (5 дней). В еженедельном отчёте и при выборе
  недели показываются только эти 5 дней; данные за субботу/воскресенье, если вдруг
  будут добавлены, в стандартный недельный отчёт не попадают (можно доработать
  отдельным просмотром, если понадобится).

## 4. Модель данных (черновая)

### `users`

| Поле | Тип | Описание |
| --- | --- | --- |
| id | uuid | PK |
| full_name | varchar | ФИО |
| email | varchar, unique | логин |
| password_hash | varchar | |
| role | enum('employee','admin') | |
| is_active | boolean | блокировка доступа |
| created_at / updated_at | timestamp | |

### `report_entries`

| Поле | Тип | Описание |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users |
| entry_date | date | дата, к которой относится запись |
| domain | varchar | домен проекта |
| task_link | varchar | ссылка на задачу |
| description | text | что сделал |
| time_minutes | integer | время в минутах |
| created_at / updated_at | timestamp | |

Еженедельный отчёт — не отдельная таблица, а вычисляемая выборка `report_entries`
по `user_id` + диапазону дат (понедельник–воскресенье), группировка на
фронте/бэке по `entry_date`.

## 5. API (основные эндпоинты, REST)

```
POST   /auth/login
POST   /auth/refresh
POST   /auth/change-password

GET    /report-entries?from=&to=          — свои записи за период
POST   /report-entries                    — создать запись
PATCH  /report-entries/:id                — редактировать
DELETE /report-entries/:id                — удалить

GET    /reports/weekly?week=2026-08-24    — свой недельный отчёт (сгруппированный)
GET    /reports/weekly/export?week=...    — .xlsx своего отчёта

# Только для admin:
GET    /users
POST   /users
PATCH  /users/:id
GET    /report-entries?userId=&from=&to=
GET    /reports/weekly?userId=&week=
GET    /reports/weekly/export?userId=&week=
GET    /reports/summary?week=             — сводка по всем сотрудникам
```

Права проверяются guard'ом по роли + по `user_id` (сотрудник не может запросить
чужие данные).

## 6. Технологический стек и архитектура

- **Frontend:** Vue 3 + TypeScript, Vite, Pinia (стейт), Vue Router, компонентная
  библиотека на выбор (PrimeVue/Element Plus/Naive UI — для таблиц и форм),
  Axios/Fetch + interceptor для JWT.
- **Backend:** NestJS + TypeScript, TypeORM или Prisma, PostgreSQL, class-validator
  для DTO, Passport (JWT strategy), ExcelJS для генерации `.xlsx`, ролевые guard'ы
  (`@Roles('admin')`).
- **Инфраструктура:**
  - `docker-compose.yml`: сервисы frontend, backend, postgres, (опционально nginx
    как reverse-proxy перед фронтом и бэком, единая точка входа).
  - `.env` для секретов (DB, `JWT_SECRET`).
  - Миграции БД через TypeORM/Prisma CLI, прогон при старте контейнера backend.

```
docker-compose.yml
├── postgres      (postgres:16)
├── backend       (Nest, порт 3000)
├── frontend      (Vue, собранный статикой, отдаётся nginx)
└── nginx         (реверс-прокси: / → frontend, /api → backend)
```

## 7. Нефункциональные требования

- Валидация всех форм на фронте и бэке (DTO + class-validator).
- Часовой пояс — единый (например, МСК), даты хранить в UTC, отображать в локальной
  TZ компании.
- Пароли — bcrypt/argon2 хэш, никогда в открытом виде.
- Логи ошибок на бэкенде.
- Адаптивная вёрстка (desktop в приоритете, но форма подачи отчёта должна нормально
  работать и с телефона).
- Резервное копирование БД — вне рамок MVP, отметить как эксплуатационную задачу.

## 8. Зафиксированные решения

| № | Вопрос | Решение |
| :---: | --- | --- |
| 1 | Редактирование/удаление задним числом | Разрешено за любой прошедший день, без ограничения по сроку |
| 2 | Дедлайн подачи отчёта / напоминания | Не нужны |
| 3 | Начало/конец недели | Понедельник–пятница (5 рабочих дней) |
| 4 | Формат экспорта для админа | Отдельный файл на сотрудника + отдельный вариант экспорта по всем сотрудникам (лист на каждого) |
| 5 | Команды/тимлиды | Не нужны. Только 2 роли: сотрудник видит только своё, админ — всех |
| 6 | Лимит часов в день | Жёсткой блокировки нет; в UI — ненавязчивая подсказка, что задача обычно не больше 8 часов |

## 9. Этапы разработки (предложение)

**MVP (этап 1):**

- Аутентификация, роли
- CRUD записей отчёта у сотрудника
- Еженедельный отчёт (просмотр) для сотрудника
- Экспорт в Excel (свой отчёт)
- Админ: список сотрудников, просмотр отчёта любого сотрудника

**Этап 2:**

- Сводный отчёт по всем сотрудникам для админа
- Экспорт сводного отчёта
- Управление пользователями (создание/блокировка) из UI

**Этап 3 (опционально, по желанию заказчика):**

- Интеграция с Bitrix24 API (автоподстановка названия задачи по ссылке)
- Прочие доработки по запросу
